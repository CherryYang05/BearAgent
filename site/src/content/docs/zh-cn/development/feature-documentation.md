文档不是代码完成后的宣传稿。它要让后来的人知道做了什么、为什么这样做、从哪里验证，以及哪些
能力仍未实现。要做到这一点，不是把同一段 Spec 复制到四个地方，而是让每个页面承担不同问题。

## 四个位置各写什么

| 位置 | 回答的问题 |
|---|---|
| `docs/` | 精确需求、技术决定、实施步骤和项目状态是什么？ |
| 学习页 | 读者为什么需要这个能力，它在一次任务中怎样起作用？ |
| 开发者页 | 代码从哪里进入，修改时有哪些边界，怎样验证？ |
| 当前状态页 | 这个版本现在到底能做什么、不能做什么？ |

一个页面不需要重复另外三个页面的全文。学习页用连续例子解释，开发者页提供代码路径和测试入口，
Spec 保留可验收的精确约束。

## 从一次代码阅读问题到文档

如果读者问“Reducer 为什么叫这个名字”，不要把聊天问答原样贴进页面，也不要把 `Reducer` 换成
一个更长的新词。先用代码和测试确认：它逐条合并 Event 得到 `RunState`；然后把这段行为放进
状态教程，再说明这种函数通常叫 reducer。

同理，遇到难懂句子时应重写论述，而不是替换名词：

> 同一组测试分别跑在内存和 SQLite 实现上。两种实现对追加、冲突和读取顺序给出相同结果，
> 因此调用方换存储时不用改变使用方式。

这段话可以直接对照测试结果，也保留了 `contract suite`、port 和 adapter 的准确含义。

## Feature 关闭前

1. 更新 Spec、Plan、相关 ADR 和架构中的事实；
2. 用一个具体场景更新学习路径，第一次出现的术语说明它的工作；
3. 更新开发者入口、调用关系、失败边界和验证命令；
4. 在状态页只陈述已有代码和测试支持的能力；
5. 连续阅读改动后的段落，确认标题、上下文和术语自然；
6. 运行工程文档链接检查、站点构建和该 Feature 的完整验证。

关闭整个 P 阶段时，还要更新 Roadmap、学习地图和阶段结果，让新增 Feature 能连成一个完整用户流程。

## 外部资料只帮助解释

论文、官方文档和参考项目可以帮助发现问题或比较方案，但不能证明 BearAgent 已经实现相同能力。
引用时明确写出借鉴点，并在页面上区分通用原理、已接受设计、当前实现和未来计划。
