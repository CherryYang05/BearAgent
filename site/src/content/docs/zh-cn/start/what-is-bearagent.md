BearAgent 是一个本地优先的个人 Agent 运行时。它先让仓库与文档类长任务真正跑通，再确保每一步可查看、失败后不乱重试、危险操作必须获得授权。

:::note[内容状态：设计目标]
这一定义描述项目已经接受的方向，不表示所有能力现在都已实现。请同时查看[当前实现状态](../project/status.md)。
:::

## 为什么需要一个运行时

让模型回答问题或调用一次工具并不难。任务持续较长时间并修改文件后，会出现更实际的问题：

- 模型可能不断循环或超出预算；
- 工具可能超时，文件可能已经写入却没有留下成功记录；
- 进程可能在任务中途退出；
- 模型可能请求它本来不该使用的工具；
- 最终答案看似正确，执行过程仍可能违反规则。

BearAgent 在模型外面增加一个运行时，负责限制、记录、恢复和授权。它要回答：

1. 做过什么，用户能否查看？
2. 中断后哪些操作可以继续，哪些必须停住？
3. 这个操作是否获得了足够权限？

如果一个外部写入可能已经发生，但系统暂时无法确认，BearAgent 会把它标记为 `UNKNOWN`。这只是“结果未知”，不等于失败，也不会被自动重做。

## 第一个可用场景

P1 将交付一个仓库与本地文档研究助手。它只能在指定工作区读取资料，并把报告或说明写入 `outputs/**`。P1 不包含联网搜索。

同一组任务会继续用于：

- P1：证明任务可以完成，而且过程可查；
- P2：证明进程中断后不会乱重试；
- P3：证明危险操作需要授权，而且代码只能在隔离环境运行。

## 为什么第一版很小

项目首先限制为单用户、单 Agent、单进程、SQLite 和命令行优先。Web UI、MCP、Memory、多 Agent 和浏览器控制都不会抢在前三个闭环之前。

## 当前能做什么

目前已实现不依赖特定模型服务商的 ID、Message、Error、Event 通用外壳、SQLite EventStore 与真实模型
适配器；Agent Loop 和工具仍属于后续 P1 Feature。因此现在最适合做的是阅读内部数据规则和参与构建，而不是把它当作
已经可用的个人助理。
