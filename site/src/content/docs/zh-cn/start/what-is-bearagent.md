一次模型调用结束得很快，失败了通常也可以重新问。但一次 Agent 任务可能持续几分钟，期间读取
多个文件、调用多次模型，还可能写出结果。此时“再试一次”并不总是安全：文件也许已经写好，
只是成功记录来不及保存。

BearAgent 是承接这类执行工作的本地优先 Runtime。模型负责提出下一步，Runtime 负责记录状态、
限制资源、调用工具和执行权限判断。任务记录和产物默认留在用户自己的电脑或服务器。

:::note[P1 已完成，恢复与授权仍在规划]
本页说明 BearAgent 的产品方向。P1 已完成可检查执行；P2 的恢复语义和 P3 的授权/隔离尚未实现。
当前事实请看[当前实现状态](../project/status.md)。
:::

## 用一个任务来看职责

用户提出：

> 阅读 `docs/` 中与架构有关的内容，写一份不超过 800 字的介绍到 `outputs/intro.md`。

完成这件事至少需要以下判断：

- 模型下一步想读哪个文件？
- 请求的路径是否仍在允许的工作区内？
- 本次任务还有多少模型调用、token、时间和工具次数？
- 写文件之前是否需要额外授权？
- 工具超时后，文件究竟没写、写了一半，还是已经替换成功？
- 用户怎样看到最终文件以及中间发生过的错误？

模型只回答第一个问题。其余问题属于 Runtime。

## 为什么强调“结果不明就停下”

读文件失败通常可以重试；付款、发布或覆盖文件却不能随便重做。如果外部操作可能已经发生，
但 Runtime 没有收到可靠结果，BearAgent 将来会把该次 Activity 标为 `UNKNOWN`。它表示“目前
无法确认”，既不是成功，也不是失败。P2 才会实现这套恢复处理，当前代码尚不支持。

## 第一版有意很小

P1 至 P3 固定为单用户、单 Agent、单个 Runtime 进程、SQLite 和命令行。首个任务只读取指定工作区，
并只向 `outputs/**` 写入。P2 先解决安全恢复，P3 再解决授权和隔离；联网搜索、HTTP/Web UI、MCP、
Memory 和多个 Agent 都排在后面。

这样做不是否认这些功能，而是先回答更重要的问题：一个动作发生过吗，为什么允许它发生，
进程中断后还能否根据已有事实作出可靠判断。

想先实际操作，直接进入[P1 命令行完整使用手册](../guides/cli.md)；想按概念逐步理解，进入
[P1 主学习路线](../learn/)。
